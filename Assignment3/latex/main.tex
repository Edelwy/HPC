\section{Implementation}

The project structure and details of all implementations can be found in our \href{https://github.com/Edelwy/HPC/blob/3a6c459ccaec52d97bcd7c4595b12c051d74e0f5/Assignment3/readme.md}{\textbf{repository description}}. We support animation output, writing the final state, and printing energies at every step.

First we improved the \href{https://github.com/laspp/HPC/blob/2472513da1348693fd3adbfefac1a6728f4fba4e/labs/04-Assignment3-CUDA/src/lennard-jones/src/lennard-jones.cu}{original \textbf{sequential version}} by applying \textbf{Newton's third law}. In this way we avoided iterating over all ordered pairs and iterated only over unordered pairs. We also precomputed some values and avoided functions such as \texttt{sqrt} and \texttt{pow}. These improvements are present in the other implementations as well.

We kept the Newton's third law improvement in the \textbf{OpenMP} version as well. We used two separate flat arrays for the forces and applied \textbf{array reduction}, where each thread gets a private copy of the array and updates that copy independently. Afterwards OpenMP adds all copies together as a point-wise sum. We also used \textbf{dynamic scheduling}. When a thread finishes its chunk, it requests the next free chunk rather than using fixed chunks upfront, because the outer loop is uneven.

Then we implemented three different \textbf{CUDA} implementations. The first was the basic implementation over the entire ordered pairs loop. We tried different block sizes, from $32$ to $512$. Energies are computed on the host when necessary, while the force computation is done on the device. From this version we then branched into two different optimizations.

Since forces are limited by $r_{cut} = 2.5\sigma$, we can consider only pairs that matter. The entire box is split into \textbf{square cells} with side length at least $r_{cut}$. Therefore we only need to look at the neighbouring $8$ cells. First we bin how many particles are in each cell and which particle indices belong to it. This is done on the device. Then we compute the new forces, again on the device, but only checking the particles own cell and its neighbouring cells.

The second CUDA optimization was to use \textbf{shared memory} and store particles as several arrays instead of one array of structs. This version still iterates through all ordered pairs, so it is comparable with the basic version. We divided the particle array into tiles, each of size equal to the block size. Shared memory was used to store the $x$ and $y$ coordinates of each tile. Instead of reading the entire particle array from global memory repeatedly, we first load one tile into shared memory, compute the interactions, and then move on to the next tile.

The best performance was observed for the \textbf{CUDA cell-list} implementation (\textit{\texttt{CELLS}}) with block size $128$. Shared memory also helped (\textit{\texttt{OPT}}), however, the best approach would probably be to combine both. It is interesting that shared memory still sped up the basic implementation considerably, and would likely perform even better for larger particle counts.

It is also interesting that the strong \textbf{OpenMP} version with Newton's third law was comparable to basic CUDA. In fact, it was faster in all measured cases. That gap shrank at larger particle counts and would likely reverse for still larger $N$. Against the CUDA cell-list implementation, however, OpenMP remained much slower throughout.
