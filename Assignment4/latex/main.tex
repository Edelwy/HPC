Our scripts and modified source code can be found in our \href{https://github.com/Edelwy/HPC}{\textbf{GitHub} repository}. \href{https://chakazul.github.io/lenia.html}{\textbf{Lenia}} is a continuous cellular automaton generalising the Game of Life. A more detailed report is available in the repository.

\section{Implementation}

First we improved the initial \textbf{sequential version}, analogously to what we did \href{https://github.com/Edelwy/HPC/blob/main/Assignment2/src/src/lenia_opt.cu}{Assignment 2}. The improved verison was three times faster than the one provided and we use the improved one as the basis for all our speed comparisons. 

Then we implemented three \textbf{MPI} versions. Every rank runs the same program, but inside the evolution function each rank owns a piece of the grid and communicates \textbf{halos}. In the first version the piece of the grid is a \textbf{row}. We compute the row partition by dividing the number of rows among the processes. Any remainder is distributed by assigning one additional row to the lowest ranks until all remaining rows have been allocated. We send the strips of the world to rank via \texttt{MPI\_Scatterv}, we transfer halos via \texttt{MPI\_Sendrecv} and gather the strips at the end via \texttt{MPI\_Gatherv}.

We implemented a version that uses a \textbf{block distribution} as well. Here we had to manually send data to each block using \texttt{MPI\_Send}. We created the block using the \texttt{MPI\_Dims\_create} in-built method. Then we created a Cartesian-coordinate communicator with modulo wrap-around on both dimensions using \texttt{MPI\_Cart\_create}. We also used a couple other methods for obtaining coordinates and neighbours. In the block distribution version we implemented a \textbf{custom MPI datatype} in order to improve the transaction of left and right halos.

Finally, we tried to \textbf{reduce communication overhead} by doing more computation. We tested whether introducing bigger paddings and then making sequential substeps would improve or slow down our algorithm. We implemented a new version of the row distributed method, where it takes in a parameter $K$ which represents the number of substeps that should be done sequentially.

As one can see from the above numbers and speed-ups below the \textbf{32-rank version was fastest} in all cases. It outperformed other alternatives even on small grids, which was not necessarily obvious due to communication overhead, however the speed-up increased with grid size. The \textit{MPI} overhead was too small to make the 1-rank version slower than the sequential one, actually, it was slightly faster. This is likely due to minor differences in the inner loop, but the speed-up is negligible. The block grid division slightly outperformed the row division on all accounts. The best speed-up from row to block method was $1.95$ for $128 \times 128$ grid on 16 ranks. The derived data types used in the block-rank method also contribute to the speed-up.

All the previous versions were tested on \textbf{one node}. We also tested both row and block implementation on \textbf{two nodes} by assigning each node half the processes. For size $1024 \times 1024$ and $4096 \times 4096$ on 16 and 32 processes barely produced any difference. The only difference that was not negligible was for the grid $1024 \times 1024$ on 16 processes which was roughly $12\%$ slower on 2 nodes for row-rank method.

Finally, we tried \textbf{reducing communication overhead} by taking a larger padding and updating it on $K$ steps. We tested this for the two larger cases where it makes most sense due to the size of the halo being quite large for larger $K$ and on the two best-performing rank sizes. This actually made the algorithm slower, with slow-down increasing with the size of $K$.
